# ADR 0001：整體架構與資料契約

狀態：已採納（2026-08-04）

## 背景

前身專案 `taiwan-credit-card-promotions` 已上線並覆蓋 17 家銀行、1,069 筆活動。
它做得好的部分（發布防護、清單指紋快取、網域白名單貫穿 redirect）值得沿用；
但實測顯示它的資料模型無法回答使用者的第二個核心問題「這活動我拿不拿得到、
會不會白刷」。本 ADR 記錄新專案的架構決策與取捨理由。

## 實測到的結構性問題

**問題一：時間衍生狀態被凍結在資料檔裡。**
`lifecycle` 在產生資料時算好寫入 JSON，前端直接拿來做篩選與 badge。資料 08-01
產生、08-04 開啟，線上第一張卡（`start_date=2026-08-03`）掛著「即將開始」。
前身的 PR #2 已經認出「時間衍生狀態不該凍結」這個原則並修好了 agenda，
但沒有窮舉同類 —— `lifecycle` 是一模一樣的問題。

**問題二：解析不到就填固定值，把「未知」偽裝成「已知」。**
登錄視窗解析不到結束時間時填 `start + 30 分鐘`（後改 15 分鐘）。全站 388 個
視窗中 348 個（90%）是這種合成值。真實案例：聯邦波次登錄的原文是
「8/15下午3點開放登錄至8/20」，使用者實際有 5 天可登錄，資料卻說 30 分鐘。

**問題三：擷取管線的設計目標是「找時間點」，不是「保留活動條件」。**
`_registration_excerpt` 只保留含「登錄」二字的行。`registration_text` 長度
中位數 245 字元、達 2400 上限的 0 筆 —— 資訊是被濾網濾掉的，不是被長度砍掉的。
因此資格、門檻、分期、名額全部沒有結構化欄位可用。

**問題四：活動粒度錯誤。**
以明細頁 URL 雜湊當活動 ID，一頁一筆。但實測玉山 momo 頁含「活動一／二／三」
各有自己的登錄時間與名額，中信一頁 14 個活動。合併後各子活動的登錄時點互相
污染，產生「活動至 08-15 卻有 08-17 登錄時點」這類矛盾資料（全站 5 筆）。

**問題五：抽象化做了一半。**
17 個 extractor 中 9 個共用 `_listing_promotions`，另外 8 個各自手寫完整流程
（`extract_yuanta` 205 行、`extract_esun` 231 行，差異只在清單 selector 與
分頁機制）。`fetch.py` 有 4 套近乎相同的抓取實作。修一個共通 bug 要改 9 處。

## 決策

### 資料契約：三條規則

1. **只放事實，不放推導。** 時間或門檻的函數一律不進資料檔，由讀取端計算。
2. **抓不到就留 `None`。** `RegistrationWindow.end` 可為空；`kind="deadline"`
   時 `start` 可為空。用 `anchor` 屬性提供行事曆定位點。
3. **每個有風險的欄位帶 `confidence` 與 `evidence`。** UI 據此區分確定與推測，
   並讓使用者展開原文核對。

### 兩層模型：Campaign / Offer

`Campaign` 對應一個明細頁，`Offer` 對應一個子活動／方案。這是修正問題四的關鍵：
一個 URL 可以產生多個 Offer，各自持有獨立的期間、登錄視窗、門檻與名額。
無法可靠切分時，該 Offer 標記 `needs_review` 並在 UI 顯示「本頁含多個活動，
請至官方頁確認」，不得把所有時點合併後假裝成單一活動。

### 階梯門檻

依聯邦銀行明細頁實測修正：門檻不是單一數字。原文的 `dt`/`th` 欄位名直接就是
欄位定義（單筆分期門檻／回饋刷卡金／分12期以上回饋升級／每波限量登錄名額），
值是四階（35,000→700 元／50,000→1,000 元／65,000→1,300 元／75,000→1,500 元），
每階有自己的名額。因此 `threshold_tiers` 是陣列。

### 時序契約是一等公民

前身用 `registration_required: bool` 把「登錄與消費的先後關係」壓成布林值。
新模型以 `TimingContract` 明確表達四型，並計算 `spend_counts_from`、
`last_chance_to_register`、`spend_days_left_after_registering`，讓前端能畫出
雙軌時序帶（可消費期間 vs 可登錄期間），一眼看出真正有效的消費區間。

### 時間解析：tokenizer + 狀態機，不用正則疊加

前身在 `_registration_windows` 疊了六層正則，各自帶一套上下文判斷，再用
`seen` 與 `range_spans` 手工去重。優先權是隱含的：秒級時間讓第一層失配後
默默掉到第三層，產出假視窗且沒有任何降級訊號。

新做法分兩階段：先掃成 token 串，再用單一狀態機以**顯式**的優先權表
（長 pattern 優先）決定每個 token 組合代表哪種視窗。任何降級都反映在
confidence 上。同一叢集內做貪婪掃描，因為一個叢集可能含多個視窗
（聯邦波次登錄的兩個波次距離很近）。

新舊在相同真實原文上的對照：

| 真實原文 | 前身 | 本專案 |
|---|---|---|
| `2026/8/7 17:00:00~2026/8/31 23:59:00 統一開放…登錄` | 0 個視窗 | `range` 08-07 17:00 → 08-31 23:59 |
| `於2026/8/17 10:00 於momo活動登記頁開放登錄` | 10:00→10:30（編造） | `opens_at` 10:00 → `None` |
| `8/15下午3點開放登錄至8/20 … 9/15下午3點開放登錄至10/20` | 兩個 30 分鐘假視窗 | 兩個真實區間（5 天／35 天） |
| `優惠期間：115年1月1日～115年12月31日止 … 免費登錄享…` | 正確排除 | 正確排除 |

### 抓取層：宣告式 adapter，不是每家一個函式

每家銀行用一份 TOML 描述「怎麼拿到清單」與「怎麼拿到明細」，涵蓋三種型態
（`json_api` / `html_list` / `form_paged`）。真正詭異的才寫 override，上限 30 行。
新增一家銀行是「加 30 行設定 + 一個 fixture」，不是「加 200 行 Python」。

實測到的 adapter 必要能力：
- `detail.source` 必須可宣告 `html | api | none` —— 國泰世華明細頁只有 31 字
  （SPA 渲染），必須走 API 的 `campaignProps`
- `detail.cardinality` 必須可宣告 `one | many` —— 中信一頁 14 個活動
- 明細分段要吃純文字 + 關鍵字錨點。實測 7 家中只有 2 家有可辨識的
  `h2`/`dt`/`th` 標題，但 6 家的純文字都含「活動期間／活動辦法／參加資格／
  注意事項」等段落關鍵字。**不能只依賴 CSS selector。**

### 依賴策略：精選依賴，不追求零依賴

前身選擇零依賴（純標準庫），換來的是手寫 4 套 HTTP session 與一個 HTMLParser
子類。本專案採 `httpx` + `selectolax` + `pydantic`，並加上 `ruff` + `mypy --strict`
+ `pytest` 作為品質閘門。取捨：多了 lockfile 與供應鏈面，換回維護成本與型別安全。

## 沿用前身的部分

這些前身做得好，直接沿用不重寫：

- **發布防護**：多條獨立條件決定「寧可留舊資料也不覆蓋」，並加上逐來源
  覆蓋率回歸（前身的破口：212 筆的最大來源整個歸零，全站跌幅僅 19.8%，
  低於 50% 門檻會靜默發布）
- **清單指紋快取**：實測沿用 935 筆、省 798 次明細讀取
- **網域白名單貫穿 redirect 每一跳**，並加上逐筆容錯 —— 前身在單一筆連結
  非法時整次更新 exit 1
- **對「被阻擋」與「網址失效」的區分**：Cloudflare 403 時沿用已驗證快照，
  不擅自改用非官方來源
- **17 家已驗證的 `entry_url` 與 `official_domains`**

## 後果

- 新增銀行的邊際成本大幅下降，但初期要付通用 adapter 的設計成本
- 資料檔形狀與前身不相容，兩邊的前端不能互換
- golden corpus 成為必要基礎設施：沒有它就不能安全改動解析器

## 修正（2026-08-04）：不快取解析結果

本 ADR 原本沿用前身的清單指紋快取 —— 指紋未變就沿用上一版的活動資料。
實作到接輸出層時發現這個決策是錯的，在此推翻。

**問題：快取衍生輸出會讓解析器的修正無法傳播。** 指紋未變的頁面會沿用舊結果
最多 30 天。也就是說修好 `HH:MM:SS` 的解析之後，那些頁面還會繼續掛著錯的
登錄時間一個月。這正是本 ADR 開頭批評前身的「衍生狀態被凍結」，用快取把它
重新引進來很不划算。要控制它就得再加 parser 版本失效機制，複雜度又上一層。

**量測：條件式 GET 的實際涵蓋率只有三分之一。** 六家來源中只有國泰世華與
聯邦提供 ETag／Last-Modified，中信送 `no-store, max-age=0`、玉山送 `private`、
元大送 `no-cache, no-store`。所以 HTTP 層快取本身也不是解答。

**改為：快取輸入，不快取輸出。**

* 一律用當下的解析器重新推導，修正立即生效於全部頁面。
* 條件式 GET 保留為免費紅利，但存的是頁面原始 HTML（見 `pagestore`），
  收到 304 就用存檔重新推導。只快取伺服器提供驗證標頭的頁面 ——
  沒有驗證標頭就永遠收不到 304，存了用不到。尊重 `no-store`。
* 快取不進版控，CI 用 `actions/cache`。命中與否對正確性零影響。
* **按銀行平行執行**（不同主機，per-host 節流仍然成立），wall clock 從
  「所有銀行相加」變成「最慢的單一銀行」。六家實測在 115 秒內完成。

**代價評估。** 不快取衍生輸出的代價是每次重抓約 800 頁（沒有驗證標頭的那些
來源）。平行執行後 wall clock 約 3 分鐘，對銀行的請求率約 0.5 req/min 持續，
對銀行官網不構成負擔，GitHub Actions public repo 的分鐘數免費。用 3 分鐘換掉
一整個子系統加一類 staleness bug 是划算的。

順帶一個佐證：本專案第一版那個「第二次執行筆數從 223 掉成 92」的 bug
（304 沒有 body，卻被當成頁面內容），根源就是衍生快取那條路徑的存在。
拿掉它，那個 bug 的可能性就不存在了。
