# ADR 0002：抓取要跑在哪裡

狀態：已採納（2026-08-04）

## 背景

前身專案的 workflow 名為 "Refresh and deploy GitHub Pages"，但裡面**沒有任何
refresh 步驟、也沒有 cron**。真正的更新靠本機的 Codex cron 排程（每月一日、
每週一），排程結果 commit 後推上來。這個落差沒有寫在 repo 裡，讀者會合理推論
它是雲端自動化。

這個安排在 2026-08-01 到 08-04 之間造成資料流中斷三天：

| 時間 | 結果 |
|---|---|
| 08-01 01:04 | 成功，1,079 筆 |
| 08-01 08:02 | 發布防護攔下：16/17 來源失敗、13 個 DNS 失敗，重跑仍失敗 |
| 08-03 01:49 | 攔下，重跑因單一來源逾時而 exit 1 |
| 08-04 10:31 | 攔下，同樣 16/17、13 DNS |

根因不是銀行封鎖。在同一台機器互動式執行同一份程式碼，對那 13 個「DNS 失敗」
名單中的 6 家做對照測試全部成功（HTTP 200，0.6–2.2 秒）。問題出在**排程執行時
套用的沙盒網路策略**。

防護機制本身完全正確（正確攔下、保住舊資料、每次都發 Slack 警示），但
**警示發了三天沒被處理，而網站上完全看不出資料已經過期**。

## 決策

### 一、抓取跑在 GitHub Actions cron，self-hosted runner 作為 fallback

理由：失敗必須是**可觀測**的。Actions 有執行紀錄、job summary、失敗通知，
排程本身壞掉時看得出來；本機沙盒的網路策略變更是靜默的。

已知風險：部分銀行封鎖 datacenter IP（前身實測陽信與第一銀行對自動化請求
回傳 Cloudflare 403）。因此第一步是實測 17 家對 Actions runner 的可達性，
被封的來源才路由到 self-hosted runner（住宅 IP）。

### 二、網站必須自己顯示資料新鮮度

`generated_at` 超過 36 小時就在頁面上顯示明確的過期提示。理由：上面那三天的
中斷，Slack 警示有發、防護有動作、但使用者在網站上看到的是一個看起來正常
運作的站台，只有頁首一行小字寫著日期。**靜默失效必須在使用者看得到的地方
變成不靜默。**

### 三、逐筆容錯，不讓單一筆拖垮整次執行

前身在單一活動連結未通過白名單時（彰化銀行官方頁曾吐出
`http://10.100.6.38/frontend/bonusDetail.jsp?id=3450`，內網 IP + 明文 http），
例外往上冒導致整次更新 exit 1，其餘 16 家一起失敗。

新設計：白名單本身**不放寬**（拒絕私有 IP 與非 https 是正確的），但被拒的
連結降級為「跳過該筆並記錄到來源健康與警示」，讓整次執行仍能完成。
官方頁自身異常（私有 IP、非 https）產生獨立的警示類別，與「來源失效」區分。

### 四、workflow 的名字必須說實話

三個獨立 workflow，各自只做名字說的事：

- `scrape.yml` —— cron 觸發，抓取並開 PR。不部署。
- `verify.yml` —— PR 閘門：ruff、mypy、pytest、golden corpus diff、
  逐來源覆蓋率回歸。不抓取、不部署。
- `deploy.yml` —— 只在資料或前端變更時部署。不抓取。

## 後果

- Actions runner 被銀行封鎖的比例決定了 self-hosted 的必要性，這要實測才知道
- self-hosted runner 需要機器常開，這是使用者要承擔的營運成本
- 抓取改開 PR 而非直接推 main，多一個合併步驟，但換到可審閱的資料 diff

## 修正（2026-08-06）：failed／blocked 的來源不該否決其餘來源

2026-08-06 的 CI 執行被發布防護擋下：華南逾時（30 → 0 筆）、陽信被 datacenter
IP 封鎖（24 → 0 筆），兩家合計佔全站 1,538 筆的 **3.5%**，卻讓其餘 15 家正常
來源的更新全部停止。

這正是本 ADR 開頭記錄的前身病灶重演，只是換了觸發原因：**防護正確擋下、警示
有發、job 有失敗紀錄，但使用者看到的是一個看起來正常運作的過期網站。** 而且
陽信的封鎖是持續性的，等於永久停更。

**決策：逐來源覆蓋率退步分成兩類判斷。**

* **回報 complete 卻筆數崩掉** —— 靜默流失，沒有別的訊號，一律照 40% 門檻擋。
  這是這條檢查的本業（前身的破口就在這裡）。
* **已經以 failed／blocked 大聲回報** —— 它們的筆數本來就是 0，且已有來源健康度、
  警示、網站「來源狀態」面板三個出口。只有**合計流失達到全站 15%** 才擋。

門檻取在兩個實測案例之間：前身 2026-08-01 台北富邦 212 筆佔 19.8% 歸零（必須
擋，使用者會少掉五分之一的活動）；本次華南＋陽信合計 3.5%（不該擋）。
「一次掛一片」仍由 systemic／catastrophic 兩條負責（≥3 家或 ≥50%）。

## 實測結論（2026-08-06）：datacenter IP 的封鎖範圍比預期小得多

本 ADR 原本寫「部分銀行封鎖 datacenter IP（前身實測陽信與第一銀行對自動化請求
回傳 Cloudflare 403）」，並把「實測 17 家對 Actions runner 的可達性」列為第一步。
現在有結果了：

| 來源 | CI 結果 | 說明 |
|---|---|---|
| 第一銀行 | **complete，178 個活動頁、0 阻擋** | 舊註記說會被拒，是錯的 |
| 元大 | complete，57 筆 | 本機反而會 403（住宅 IP 被擋） |
| 陽信 | **blocked** | 換純 Chrome UA 無效，**看的是 IP** |
| 華南 | failed（逾時） | 本機 0.8–1.9 秒；已加重試 |
| 其餘 13 家 | complete／partial | 無 IP 問題 |

所以 self-hosted runner 只為**陽信一家**（24 筆、佔全站 1.6%）而存在。這個成本
效益比不值得預設採用，改為：陽信誠實顯示為 blocked，等使用者決定是否提供常開
機器。元大的方向剛好相反 —— 它在 CI 通、在住宅 IP 被擋，所以「換住宅 IP 就都
會通」的假設本身也不成立。

**transport 加上暫時性故障重試。** 原本完全沒有重試，一次逾時就讓整個來源歸零。
現在逾時、連線失敗與 5xx 重試 3 次（退避 1s／3s）；403／401／429 明確不重試 ——
那是「拒絕自動化存取」，重試只會更像攻擊。
